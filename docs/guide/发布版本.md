# 维护、发布与下载

本 fork 的正式发布入口：[lyhzzz16/FloatingX-Harmony Releases](https://github.com/lyhzzz16/FloatingX-Harmony/releases)。当前版本为 0.2.0，不使用业务后缀，也不照抄 Android 库版本号。

## 分支与版本

- main 保存经过 PR 和核心测试的集成代码。功能和修复在独立分支完成，经 PR 合并；不直接推送 main，不强推、不删除 main。
- 当前个人维护阶段要求 PR、core-tests 成功、讨论已解决；审批人数设为 0，避免只有一个维护者时无法自审的死锁。有独立维护者加入后再提高审批要求。
- 每个公开版本创建一个附注标签，例如 v0.2.0，固定到 main 上的确切提交。v* 标签不允许改写或删除；发现缺陷发布新版本。
- patch 版本修复兼容问题，minor 增加能力或调整 0.x 阶段契约；破坏性变化必须说明迁移步骤。正式发布不隐藏已知限制。

## 定包流程

1. 在发布分支更新 floatingx/oh-package.json5、Index.ets、package.json/lock、示例 manifest/lock 与 AppScope 版本。versionCode 单调递增；保留已有文件 EOF，避免格式改写。
2. 运行核心测试及发布工具测试。仅版本/文档改动也需检查所有版本一致。签名、证书、local.properties 和构建输出不得提交。
3. 使用配套 DevEco/HarmonyOS SDK 构建正式 HAR 和未签名示例 HAP，明确选择 release 构建模式；通过 IDE 操作执行。构建/清理授权遵循使用方项目要求。
4. 检查 HAR 内版本常量、源文件与待发布提交完全一致；检查 HAP/模块元数据中的版本、实际编译 SDK 和模式。记录本机签名配置只影响本地安装，公共附件仅使用 unsigned HAP。
5. PR 合入 main 后，把标签指向该发布提交，创建草稿 Release；上传 HAR、unsigned HAP、manifest.json、SHA256SUMS，再校验下载结果后发布。源码与产物必须可追溯；不覆盖已公布的不同内容。
6. 消费者下载指定版本并验证校验值，再更新自己的本地 HAR 依赖和 lock，执行实际业务回归。不会自动修改消费者工程。

## Release 附件

- floatingx-vX.Y.Z.har：业务使用的库。
- floatingx-demo-vX.Y.Z-harmonyos-unsigned.hap：未签名示例，真机需使用自己的签名配置。
- manifest.json：tag、源码提交、SDK、DevEco/Hvigor/Node 版本、构建模式及产物哈希。
- SHA256SUMS：上述附件的完整性校验。

下载后执行 `shasum -a 256 -c SHA256SUMS`。不要只改旧 HAR 的文件名当作新版本。

## CI 与工具链边界

CI 工作流对 PR/main 执行宿主核心测试和发布脚本测试；它不替代 ArkUI 编译与设备验收。

旧 Legacy API 12 release assets 工作流仅保留手动入口，用于历史 API 12 兼容版本；0.2.x 不使用它生成发布包。发布 Release 不会自动触发旧工具链重建或覆盖附件。当前完整组件使用较新的 ArkUI 手势接口，编译 SDK 不能与最低运行 API 混淆。

仓库暂不上传签名材料，也不为自动构建把个人开发者证书放进 Actions。未来配置团队构建机时应固定合适的官方 SDK、版本与校验值，先验证产物再启用云端定包。

## 引入方式

保持与消费工程现有三方库一致的本地 HAR 方式：

```json5
{
  "dependencies": {
    "floatingx": "file:./libs/floatingx-v0.2.0.har"
  }
}
```

无需发布 OHPM 即可使用。多个项目确有统一分发需求时再选择获授权的内部注册表，不占用上游作者的包命名空间。
